# 08 · 配置驱动的检测流程（场景剧本）

> **一句话**：检测软件只调用极少、稳定的 API 触发“阶段”（检测前/中/后……），**每个阶段做哪些 MES 交互全部来自配置文件**。换工厂只换配置，检测软件代码零改动；`Enabled=false` 时所有调用变成安全空操作。

本章介绍“场景剧本”（Workflow）层：它架在[统一客户端 `IMesClient`](./04-API参考.md) 之上，把“检测前取工单、检测后上报结果、不合格就报警……”这类**编排逻辑**从代码挪进 `appsettings.json`。

- 适合谁：希望“一套检测软件对接不同工厂 MES”的团队——面对工厂 A（REST）、工厂 B（MQTT）……检测软件**不改一行代码**，只换一份配置。
- 不适合做什么：它**不是**可视化流程编辑器，也**不引入脚本语言**；`When` 条件只做必要的轻量比较（见下）。

---

## 1. 心智模型

```
检测软件（你的代码，跨工厂不变）
   │  启动： var mes = MesWorkflows.Create(configuration);          // 或 DI: IMesWorkflowHost
   │  检测前： await mes.RunAsync("BeforeInspection", ctx);
   │  检测后： await mes.RunAsync("AfterInspection", ctx);
   ▼
场景剧本引擎 IMesWorkflowHost（本章）
   │  读取 Mes.Workflows[阶段] 的有序步骤，逐步执行
   ▼
统一客户端 IMesClient（第 04 章）→ 协议 Provider（REST/MQTT/…）→ 工厂 MES
```

检测软件只跟**阶段名**和**上下文**打交道，既不关心底层协议，也不关心“这个阶段具体调用了哪些 MES 操作”。后者完全由配置决定。

---

## 2. 配置结构（Schema）

在既有 `Mes` 配置节下新增 `Enabled` 总开关与 `Workflows`（阶段 → 有序步骤列表）：

```jsonc
{
  "Mes": {
    "Enabled": true,                       // 总开关：false 时所有 RunAsync 都是空操作
    "ConnectionString": "rest://mes.factoryA.local/api?token=...",
    "OperationBindings": [ /* 可选：操作→通道(URL/主题/SQL…) 映射，见第 03 章 */ ],

    "Workflows": {
      "BeforeInspection": [
        { "Operation": "GetWorkOrder", "Args": { "workOrderId": "{workOrderId}" }, "CaptureTo": "workOrder", "Optional": true },
        { "Operation": "GetRecipe",    "Args": { "recipeId": "{recipeId}" },       "CaptureTo": "recipe",    "OnError": "Continue" }
      ],
      "AfterInspection": [
        { "Operation": "ReportInspection", "PayloadFrom": "inspectionResult" }
      ],
      "OnFail": [
        { "Operation": "RaiseAlarm", "When": "outcome == Fail",
          "Payload": { "code": "AOI_NG", "text": "SN {serialNumber} 不合格" } }
      ]
    }
  }
}
```

> 配置文件支持 `//` 注释与尾随逗号（.NET JSON 配置提供程序默认允许）。

### 2.1 步骤字段

| 字段 | 必填 | 含义 |
| --- | --- | --- |
| `Operation` | ✅ | 操作键：内置键（见 [04 · 操作目录](./04-API参考.md)，如 `GetWorkOrder`/`ReportInspection`/`RaiseAlarm`）或经 `OperationBindings` 映射的自定义键。 |
| `Args` | | 参数名 → 模板字符串。占位符 `{var}` 从上下文取值（复用现有 `TemplateEngine`，支持 `{var:url}` 等修饰）。未被通道模板消费的参数会作为请求参数下传。 |
| `Payload` | | 内联请求体（键值对，值为模板字符串）。用于 `RaiseAlarm` 等需要结构化 body 的操作。 |
| `PayloadFrom` | | 请求体来源：引用上下文中的一个对象变量（如 `inspectionResult`）。与 `Payload` 二选一。 |
| `When` | | 条件表达式，满足才执行（见 §4）。不满足则该步“跳过”，不计失败。 |
| `CaptureTo` | | 把返回值写回上下文变量名，供后续步骤/软件读取（见 §3 串联）。 |
| `OnError` | | 出错策略：`Stop`（默认）/ `Continue` / `Alarm`（见 §5）。 |
| `Optional` | | `true` 时该步失败最宽松处理：不置整体失败、不中止、不报警（“尽力而为”的查询常用）。 |
| `TimeoutMs` | | 该步的超时（毫秒），覆盖客户端默认。 |
| `Name` | | 可选步骤名，仅用于结果与诊断显示。 |

## 3. 运行时上下文与“串联”

`MesWorkflowContext` 是一个字符串键的变量袋。检测软件把运行时数据放进去，步骤的 `Args/When/PayloadFrom/CaptureTo` 都基于它求值与写回。

```csharp
var ctx = mes.CreateContext()          // 或 new MesWorkflowContext()
    .Set("serialNumber", "SN-0001")
    .Set("workOrderId", "WO-1001")
    .Set("recipeId", "RC-APPEARANCE")
    .Set("outcome", "Pass")
    .Set("inspectionResult", inspection);   // 任意对象，供 PayloadFrom 引用
```

- **占位符**：`Args`/`Payload` 里的 `{serialNumber}` 取 `ctx["serialNumber"]`。
- **点路径**：支持 `{workOrder.productCode}` 这类点路径，穿透字典 / `JsonElement` / 对象属性，**大小写不敏感**（捕获回来的 JSON 对象键为 camelCase 也能命中）。
- **串联（`CaptureTo`）**：某步 `"CaptureTo": "workOrder"` 会把返回对象存入 `ctx["workOrder"]`，于是后续步骤可用 `{workOrder.recipeId}`——实现“先查工单，再用工单里的字段查配方”的链式编排，全在配置里完成。

---

## 4. 条件 `When`（内置轻量求值器）

为避免引入重量级表达式引擎，`When` 使用**内置极简求值器**，仅支持：

- 比较：`==`、`!=`、`>`、`>=`、`<`、`<=`（数值按数值比，否则按字符串比，大小写不敏感）。
- 真值：单个变量名表示“真值判断”（非空、非 `false`、非 `0`、非空串即为真）；`!var` 取反。
- 两侧可为上下文变量或字面量：`outcome == Fail`、`isPass == false`、`defectCount > 0`、`!gate.passed`。

> 不支持 `&&`/`||`/括号/函数等复杂表达式——需要复杂判断时，建议在检测软件侧算好一个布尔/枚举变量放进上下文，再用简单 `When` 判断。

---

## 5. 错误策略 `OnError` / `Optional`

每步执行后按下表决定“是否置整体失败、是否中止后续、是否报警”：

| 设置 | 整体失败 | 中止后续 | 额外动作 |
| --- | --- | --- | --- |
| `OnError: Stop`（默认） | 是 | **是** | — |
| `OnError: Continue` | 是 | 否 | — |
| `OnError: Alarm` | 是 | 否 | 自动 `RaiseAlarm`（code `WORKFLOW_<OP>`，Major） |
| `Optional: true`（优先级最高） | **否** | 否 | 不报警 |

- `Optional=true` 最宽松：常用于“查得到更好、查不到也不影响流程”的信息型查询（示例默认配置中的 `GetWorkOrder`/`GetRecipe` 即如此）。
- 结果聚合为 `MesWorkflowResult`：含每步 `Steps`（成功/跳过/失败 + 返回 `MesResult` + 耗时）、整体 `Success` 与总耗时 `ElapsedMilliseconds`。

## 6. 面向应用的极简 API

### 6.1 非 DI 入口

```csharp
using Mes;                                   // 聚合包

IMesWorkflowHost mes = MesWorkflows.Create(configuration);   // 读 Mes 配置节，内部建好客户端
// 也可：MesWorkflows.Create("rest://…")  /  MesWorkflows.Create(client, options)

var ctx = mes.CreateContext().Set("serialNumber", "SN-0001").Set("outcome", "Pass");
MesWorkflowResult r = await mes.RunAsync("BeforeInspection", ctx);
```

### 6.2 依赖注入

```csharp
services.AddMes(configuration);              // 同时注册 IMesClient 与 IMesWorkflowHost
// ...
public sealed class Inspector(IMesWorkflowHost mes)
{
    public async Task RunCycleAsync(string sn)
    {
        var ctx = mes.CreateContext().Set("serialNumber", sn);
        await mes.RunAsync("BeforeInspection", ctx);
        // …视觉算法…
        ctx.Set("outcome", "Pass").Set("inspectionResult", /* … */ null);
        await mes.RunAsync("AfterInspection", ctx);
    }
}
```

### 6.3 成员速览（`IMesWorkflowHost`）

| 成员 | 说明 |
| --- | --- |
| `bool Enabled` | 取自 `Mes.Enabled`。为 `false` 时所有 `RunAsync` 立即返回成功空操作。 |
| `IReadOnlyCollection<string> Phases` | 已配置的阶段名集合（便于诊断/自检）。 |
| `MesWorkflowContext CreateContext()` | 新建上下文变量袋。 |
| `bool HasPhase(string phase)` | 该阶段是否已配置且含步骤。 |
| `Task<MesWorkflowResult> RunAsync(phase, ctx?, ct)` | 执行某阶段剧本；阶段未配置/为空或 `Enabled=false` → 成功空操作。 |

## 7. 阶段名约定（可自定）

阶段名**由应用自定**，库不写死，只提供约定与引擎。推荐一套检测生命周期：

| 阶段 | 典型用途 |
| --- | --- |
| `OnStartup` | 软件就绪心跳、上报设备在线 |
| `BeforeInspection` | 过站校验、取工单/配方并缓存到上下文 |
| `DuringInspection` | 检测中的中间态上报（可选） |
| `AfterInspection` | 上报检测结果/测量/图像 |
| `OnPass` / `OnFail` | 按结论分支上报或放行/拦截 |
| `OnAlarm` | 异常时报警 |
| `OnShutdown` | 软件退出前收尾（上报离线等） |

你完全可以增删或改名——只要检测软件 `RunAsync("自定义阶段名", …)` 与配置里的键一致即可。

---

## 8. 换厂指南（只换配置）

1. 复制一份 `appsettings.json` 为 `appsettings.工厂名.json`。
2. 改 `ConnectionString`（协议/地址/鉴权），必要时加 `OperationBindings` 把操作键映射到该厂的 REST 端点 / MQTT 主题 / SQL 等（见 [03 · 协议矩阵与配置](./03-协议矩阵与配置.md)）。
3. `Workflows` 结构通常**保持不变**（各阶段做什么是业务约定，与协议无关）。
4. 检测软件按工厂加载对应配置文件即可，**代码零改动**。临时停用 MES：把 `Enabled` 置 `false`。

可运行样例见 [`samples/Mes.ConfigDriven`](../samples/Mes.ConfigDriven)：**同一份 `Program.cs` + 三份配置**（默认 `mem://`、工厂 A=REST、工厂 B=MQTT）。默认配置零外部依赖即可跑：

```bash
dotnet run --project samples/Mes.ConfigDriven        # 默认 mem://，直接可跑
dotnet run --project samples/Mes.ConfigDriven -- FactoryA   # 叠加 REST 配置（需真实服务器）
dotnet run --project samples/Mes.ConfigDriven -- FactoryB   # 叠加 MQTT 配置（需真实 Broker）
```

## 9. 设计边界（避免过度设计）

- 不做可视化编辑器、不引脚本语言/表达式库；`When` 只做必要的轻量比较。
- 复用既有操作目录、模板引擎、客户端与诊断，不改协议 Provider。
- 阶段名不写死（应用自定），库只提供约定与引擎。
